# SLIP Pretraining Corpus

The corpus SLIP was pretrained on: sensor time-series paired with captions a language model wrote.
One record is one row of one parquet shard, a series or a set of series, with four captions of it
and the name of the corpus it came from. The release also ships 11 evaluation benchmarks, which this
connector does not convert.

- **id**: `leochen085/slip`
- **source**: https://huggingface.co/datasets/LeoChen085/SlipDataset
- **licence**: MIT
- **revision**: `e5e4871a9f376ff5377ed16c598e7a84a160664a`

The connector fetches that one commit and not the repository's branch, so a later push cannot change
what a build converts.

MIT is what the release states, and it covers what SLIP added: the packaging and the captions. The
corpora SLIP assembled it from (UTSD, NormWear, Capture-24 and ChatTS) keep their own terms, and
this connector makes no claim about those.

Every number marked *(measured)* below was counted over all 17 shards at that revision.

## The source of truth

| fact | what this connector takes | the card's reading |
| --- | --- | --- |
| the columns a shard holds | the shard: **7** | `dataset_info.json` declares **9** |
| how many rows | the shards: **618,508** | the domain table sums to 448,822 |
| how many values | the shards: **1,684,610,695** | "approximately one billion time points" |
| multivariate to univariate | the shards: **0.75 : 1** | the two were sampled 2:1 |
| what the four caption columns are | four paraphrases of one caption | three levels of detail |
| which files the release ships | 17 `.parquet` shards | `state.json` names 17 `.arrow` files |

Every reading in the middle column is *(measured)*. The data wins in each row, for one reason: a
reader can re-measure it and cannot re-measure a sentence. Every losing reading is kept here rather
than deleted, because a reader who arrives through the card needs to know why the numbers differ.
The two columns `dataset_info.json` declares and no shard holds are `source_path` and `index`. The
17 `.arrow` files `state.json` names are not in the repository.

## What the description states

> This repository contains the data released alongside SLIP (Sensor Language-Informed Pretraining)
> [...] It includes two components: **(1)** the pretraining corpus of 600K+ paired sensor
> time-series and hierarchical text captions, and **(2)** 11 downstream evaluation datasets
> spanning four sensor domains.

Decides: the release is two datasets, and this connector is the first of them. The evaluation
folders have a different schema and are converted separately.

> Captions are generated at three levels of granularity — statistical, structural, and
> semantic — following the SensorLM recipe, with paraphrases generated by Qwen2-7B-IT to reduce
> template repetition.

Decides: nothing, because the values contradict it. See "Four caption fields, three caption levels".

> Qwen2-7B-IT generated three paraphrases per caption; one is randomly sampled during training.

Decides: `caption0` is the original and `caption1` to `caption3` are its paraphrases. The values
agree with this sentence.

> Captions are automatically generated and paraphrased by language models, and may contain errors
> or hallucinations.

Decides: a caption is what SLIP's generator said, not ground truth. Anyone training on these should
read it that way.

> This dataset should **not** be used for clinical decision-making. It is intended for research
> purposes only.

Decides: nothing in the conversion. It is repeated here because much of the corpus is health data.

## What one record holds

One record is one row of one shard.

**Signals.** One `TimeSeries` per inner list of the row's `time_series` column, named `s0`, `s1` and
so on in the order the row states. Every series in a row has the same length *(measured: 0 ragged
rows)*. Lengths run from 64 to 96,424 and are constant per source corpus for 31 of the 37 corpora.

The corpus states **no unit for anything**, so every series is dimensionless. It is not that the
values have no unit; it is that the release does not say what it is.

**The time axis** comes from `meta.csv`, joined on the row's `dataset` column. That join is exact
and total: all 37 corpus names match a `meta.csv` row, covering every one of the 618,508 rows
*(measured)*. A `dataset` value the table does not name stops the build with `TimeFFormatError`,
because a new corpus means a rate nobody has stated. `meta.csv` states a `Freq` per corpus, and
where it parses the series gets a `RegularAxis` at that period. Seven corpora (`BIDMC32HR`,
`ChatTS`, `EigenWorms`, `Phoneme`, `PigArtPressure`, `PigCVP` and `StarLightCurves`) state
`Freq = "-"`. That is **134,507 records, 21.7% of the release** *(measured)*, and they get an
`OrdinalAxis`: order recorded, no wall-clock rate claimed. The other **484,001** carry a real time
axis *(measured)*.

**Annotations**, all of them about the whole record and none scoped to a signal:

| key | value | where it came from |
| --- | --- | --- |
| `source_dataset` | the corpus, e.g. `BIDMC32HR` | the `dataset` column |
| `domain` | e.g. `Health` | the `category` column |
| `source_url` | where that corpus was published | `meta.csv`, through the join |
| `caption0` to `caption3` | the caption, as the release wrote it | the four caption columns |
| `all_nan_signals` | which series holds no numbers | only on the 96 rows that need it |

A caption annotation states an id of its own, `<record id>-caption0` and so on, because the tasks
answer by reference to it. Every other annotation here lets its id default.

Eight of the 37 corpora state `-` for `Source`, so their records carry `-` as their `source_url`
*(measured)*: `Capture24`, `auditory`, `dalia`, `maus`, `mendeley`, `Phyatt`, `ppg_ecg` and
`ChatTS`. The cell is what the release states, and this connector passes it through.

`category` is redundant. It is a function of `dataset`, equal to `meta.csv`'s `Domain` in all 37
cases *(measured)*. It is kept because the release ships it.

**The record id is positional**: `slip-shard-00000-row-000000`, one prefix, then the shard's number
and the row's place in it. The release ships no id of its own: the two columns that would have been
one are declared in `dataset_info.json` and exist in no shard. Two builds of the same release give
the same ids. A new release of the dataset invalidates them. A shard not named
`train-NNNNN-of-NNNNN` stops the build with `TimeFFormatError`, because the id is built from the
number in that name.

## The tasks this connector builds

| the question | type | count | scope |
| --- | --- | --- | --- |
| write this row's caption | `AnswerTask`, no prompt | **2,474,032** | the whole record |

Four tasks per record over 618,508 records, one per caption column *(measured)*. A task's answer is
the caption annotation the record carries, named through `target_annotation_ids`, and not a second
copy of the text. So a caption is reachable from the record it describes: a streamed task never
reaches `Record.task_ids`, so a caption held only by a task could be found from the task and never
from the record. The cost is that a build holds the captions in memory until the writer has walked
them.

They are flat: nothing records that `caption1` to `caption3` are rewrites of `caption0`. That
relation is real for most of the corpus and empty for the 105,085 `ChatTS` rows whose four captions
are byte-identical, so recording it would be true and uninformative for a sixth of the release.

The tasks are streamed rather than listed. Two and a half million tasks is not a list. The stream
walks the records the conversion already built, so it re-reads no shard.

## Inconsistencies and decisions

### The corpus is larger than the card's own table — **Handled**

**Problem.** The card says "600K+ sensor–caption pairs" in prose and gives a domain table summing
to 448,822. The shards hold **618,508 rows** *(measured)*. Every percentage in that table is
computed against 448,822 (Health's 237,050 is 52.82% of it), so the table is self-consistent and
disagrees with both the prose and the data. The card's "approximately one billion time points" is
also low: there are **1,684,610,695** float values *(measured)*. The split across domains does not
hold either. The table puts 52.82% of the corpus in Health and 0.58% in IoT; the `category` column
says **90,924 Health rows and 199,638 IoT rows** *(measured)*.

**Decision.** Convert every row, and carry the `category` value each row states.

**Consequence.** Anyone comparing against the card's table will find a third more data than they
expected, spread differently across the domains. That is the release, not an error in the
conversion.

### `dataset_info.json` declares two columns that exist nowhere — **Handled**

**Problem.** It declares nine features. Every shard has seven *(measured)*. The two missing ones are
`source_path` and `index`, which are precisely what a record id would have come from.

**Decision.** Take the schema from the shards. Build the record id from the shard number and the row
position, and say here that it is positional.

**Consequence.** The ids are stable across builds of this release and not across releases. A reader
who wants to trace a row back to the corpus it came from has `source_dataset`, and nothing finer.

### Four caption fields, three caption levels — **Handled**

**Problem.** The card describes three levels of granularity, statistical, structural and semantic.
The schema declares four caption fields. The values are neither: in every sampled row all four state
the same trend segments, the same cycle period, the same rounded mean, standard deviation, minimum
and maximum, and the same subject label, with `caption1` to `caption3` being `caption0` rewritten in
fluent prose *(measured)*.

**Decision.** Carry all four as annotations under the column names the release gives them, and build
one task per field. The keys state where each caption came from and claim nothing about a level.

**Consequence.** There is no way to ask this corpus for a statistical caption as distinct from a
semantic one. That distinction is not in the data.

### 105,085 rows have four identical captions — **Handled**

**Problem.** Every `ChatTS` row carries four byte-identical captions *(measured)*. The paraphraser
never ran on them.

**Decision.** Build four tasks anyway, as for every other row.

**Consequence.** A sixth of the corpus trains four times on the same string per record. Anyone
sampling one caption at random per row is unaffected, which is how the card says it was used.

### 216 captions are a paraphraser stub — **Handled**

**Problem.** 216 captions hold `Paraphrase 1:` or `The second paraphrase:` where the text should be
*(measured)*. The shortest `caption3` in the corpus is one character.

**Decision.** Convert them as they are, and warn once for the whole build with the count.

**Consequence.** 216 tasks answer with a caption annotation that holds no caption. They are findable
through the warning, and they are what the release states.

A caption column that states nothing at all is a different case, and it does not occur: every one of
the 2,474,032 cells holds a string *(measured)*. A null there would mean the release changed, so it
stops the build with `TimeFFormatError` naming the shard, the row and the column. Substituting an
empty string would invent a value and then report it as a caption that stops mid-sentence.

### 123,098 captions stop mid-sentence — **Handled**

**Problem.** 123,098 of the corpus's 2,474,032 captions, **5.0%**, do not end in a sentence-ending
character *(measured)*. They stop where the generator hit a length limit, usually on a trailing
comma: `"…the readings has no trend,"`. Some stop mid-word: `"The 60-second tri-ax"`, `"Paraph"`,
`"The"`.

**Decision.** Convert them as they are. Warn once for the whole build with the count and one
example, rather than once per caption. 123,098 identical warnings would say nothing the count does
not.

**Consequence.** One caption in twenty is an unfinished sentence. A model trained on these learns to
stop mid-sentence. Anyone using this corpus for captioning should filter on a terminating character.

### 253,587 captions carry a stray `￼` — **Handled**

**Problem.** U+FFFC, the object-replacement character, appears in 253,587 `caption0` values, 2,102
`caption2` values and 12 `caption3` values *(measured)*. It comes from `meta.csv`'s `Description`
column, where it is a document-paste artifact, and the caption generator copied it through.

**Decision.** Keep it, unchanged.

**Consequence.** 10% of captions carry a character that means nothing, and 41% of records hold at
least one. Stripping it would make the conversion differ from the release with nothing saying why;
this entry says why it is there.

### 96 rows ship a series that is entirely NaN — **Handled**

**Problem.** 96 `dalia` rows each have exactly one of their six 388-point series entirely NaN
*(measured)*. There are no partially-NaN series and no infinities anywhere in the corpus. Nothing in
the row marks it, and the caption still describes all six series.

**Decision.** Build the series, keep every value, warn once for the whole build with the count, and
add an `all_nan_signals` annotation naming which series it is on each record that has one. The NaN
is stored as the value it is, and the spec stays `nullable=False`: a null would say the release
recorded nothing there, and what it recorded is a NaN.

**Consequence.** Those records carry a series with no numbers in it. That is a fact about the
corpus, and the annotation makes it findable without scanning.

The decision costs a second read of the values. No length and no header marks an all-NaN series, so
`convert` decodes every value once to find the 96, and the loaders decode them again when the writer
asks. `convert` reads all seven columns of the 85 row groups, **4.63 GB**, and the loaders then read
the `time_series` column again, **4.28 GB**. So a build reads **8.9 GB** where reading each column
once would read 4.63 GB *(measured over the parquet bytes at the pinned revision)*.

Peak memory follows from the row groups and not from the batch. A loader hands back one whole row
group's `time_series` column, and the largest of the 85 holds **188,919,995** values, **756 MB** as
float32 *(measured)*. `convert` walks a row group 2048 rows of 7612 at a time, so it holds those
rows' values and one finiteness flag per value, both smaller than the row group they came from.

### The multivariate ratio the card claims does not hold — **Handled**

**Problem.** The card says multivariate and univariate examples were sampled at a 2:1 ratio. Across
the corpus it is 264,209 to 354,299, or **0.75 : 1** *(measured)*. The claimed ratio holds only
inside `ChatTS`, at 70,079 to 35,006.

**Decision.** Nothing to do in the conversion. Recorded because anyone reproducing SLIP's
pretraining mix needs it.

**Consequence.** None for the data.

### `state.json` names files the release does not ship — **Handled**

**Problem.** It lists 17 files named `data-000NN-of-00017.arrow`. The repository ships 17
`train-000NN-of-00017.parquet` and no `.arrow` file. It is a leftover from `datasets.save_to_disk`.

**Decision.** Ignore it. The connector reads the shards.

**Consequence.** None.

### `meta.csv` states a rate that a machine cannot read — **Handled**

**Problem.** The `Freq` column mixes a frequency (`65 Hz`), a period (`0.001 sec`, `4 sec`),
calendar words (`Hourly`, `Daily`, `30 min`), the same rate written two ways (`3h` for `ERA5
Pressure` and `3 h` for `ERA5 Surface`), and the null marker `-`.

**Decision.** `-` and an empty cell get an `OrdinalAxis`. Every other form the release uses is
parsed. A form the release has not used stops the build with `TimeFFormatError`, because guessing
at a new spelling would invent a rate. A zero is refused for the same reason: it reads as "no
rate", which is what the table already writes as `-`.

**Consequence.** 484,001 records carry a real time axis and 134,507 do not *(measured)*. A model
that needs a wall-clock rate can select on it.

## Warnings this build emits

One line for each kind, with the count and one example, through this module's logger. A property
shared by thousands of records is one fact about the release, not one fact per record.

| warning | how many it covers *(measured)* | why |
| --- | --- | --- |
| records hold a series with no numbers at all | 96 | one `dalia` series is all NaN |
| captions hold a paraphraser stub rather than text | 216 | the column holds `Paraphrase 1:` |
| captions stop mid-sentence | 123,098 | the generator hit a length limit |

## What is not built

The 11 evaluation folders of the same repository: `wisdm`, `uci_har`, `PPG_CVA`, `PPG_DM`,
`PPG_HTN`, `sleepEDF`, `ptbxl`, `wesad`, `studentlife`, `AsphaltObstacles` and `Beijing_AQI`. They
hold fixed-length windows under a different schema, so they are a different dataset.

`meta.csv`'s other columns, `Time Points`, `File Size`, `ADF`, `Forecast.`, `Description` and
`patch_size`, are facts about the corpora SLIP drew from and not about any row. They are not
converted.

The link between a row and the exact recording it was cut from. The release states the corpus a row
came from and nothing finer, so a row cannot be traced back to a subject, a session or a file.
